# Annotations (custom IFC objects)

[Widget API docs](../README.md)

StreamBIM lets users and widgets add their own objects to a building: points with a name, stored as IFC objects with `@kind: "Annotation"`. In the UI they are called *custom objects* (default name "Custom object"). They have no geometry from a model file (`layer: ""`, no `document`), can carry **attachments**, and appear in search like any other object.

From a widget you create them with `StreamBIM.API.createObject`. Everything else (reading the full record, attachments, deleting) goes through the REST API with `makeApiRequest`.

> These examples write to the project. They were run on the demo project used for verification (`npm run verify -- --include-writes` in `harness/`).

## Data model

Ember model `ifc-object` (JSON:API type `ifc-objects`), with the `with-attachments` mixin:

| Field | Annotation value |
|-------|------------------|
| `id` | New 22-char IFC-style GUID, generated by the backend |
| `properties` | `{ "@kind": "Annotation", "Name": <name> }` on create; the server adds `Global Id`, `@Building Storey` (floor by position), `BaseType: "ifcelement"` and empty `Long Name`, `Description`, `uri` |
| `center` | Point in **store coordinates**: widget `[x, y, z]` is saved as `[x, z, -y]` |
| `bbox` / `boundary` | Degenerate box at the centre / `null` (a point object) |
| `layer` | `""` (model objects have their IFC file's layer). The UI treats empty layer as *user created* |
| `building` | Current building |
| `groups` | Server-computed property groups: `Location` (floor by position), `Geometry`, and `Custom` (Created/Updated At/By) |
| `relationships.attachments` | Attachment records (files, images) |

## Create

`createObject({ center, name })` builds the record in the StreamBIM page and saves it. It resolves with the new id.

#### Create an annotation at the camera and read it back

```js
const { position } = await StreamBIM.API.getCameraState();
const id = await StreamBIM.API.createObject({ center: position, name: 'Docs example annotation' });
const info = await StreamBIM.API.getObjectInfo(id);
return { id, widgetPosition: position, storedCenter: info.center, properties: info.properties, layer: info.layer };
```

## Read the full record over REST

`getObjectInfo` returns the viewer's cached copy. The REST record has the server-side groups and the attachments relationship.

#### GET /v2/ifc-objects/{id}

```js
const projectId = await StreamBIM.API.getProjectId();
const buildingId = await StreamBIM.API.getBuildingId();
const [id] = await StreamBIM.API.findObjects({ key: '@kind', value: 'Annotation', limit: 1 });
const { data } = JSON.parse(await StreamBIM.API.makeApiRequest({ url: '/project-' + projectId + '/api/v1/v2/ifc-objects/' + id + '?building=' + buildingId }));
return {
  id: data.id,
  properties: data.attributes.properties,
  groups: data.attributes.groups.map((g) => ({ label: g.label, keys: g.content.properties.map((p) => p.key) })),
  relationships: Object.fromEntries(Object.entries(data.relationships).map(([k, v]) => [k, v.data])),
};
```

## List annotations

Annotations are searchable by `@kind`. Model files can also contain IFC annotations (e.g. Revit model lines exported as `IfcAnnotation`); tell them apart by `layer` (non-empty for model objects).

#### User-made vs model annotations

```js
const ids = await StreamBIM.API.findObjects({ key: '@kind', value: 'Annotation', limit: 100 });
const rows = [];
for (const id of ids) {
  const info = await StreamBIM.API.getObjectInfo(id);
  rows.push({ id, name: info.properties.Name, userCreated: !info.layer });
}
return rows;
```

## Attachments on an annotation

Files are attached through the attachments API (upload ticket → S3 upload → attachment record with `parent-ifc-object`). See [attachments.md](../../api/attachments.md) for the upload flow. Reading what is attached:

#### Attachments of each annotation

```js
const projectId = await StreamBIM.API.getProjectId();
const buildingId = await StreamBIM.API.getBuildingId();
const ids = await StreamBIM.API.findObjects({ key: '@kind', value: 'Annotation', limit: 20 });
const out = {};
for (const id of ids) {
  const res = JSON.parse(await StreamBIM.API.makeApiRequest({ url: '/project-' + projectId + '/api/v1/v2/attachments?filter[object]=' + id + '&filter[building]=' + buildingId }));
  out[id] = res.data.map((a) => ({ id: a.id, name: a.attributes.name || a.attributes.filename, category: a.attributes.category }));
}
return out;
```

## Delete

There is no widget method. The StreamBIM UI deletes with Ember Data `destroyRecord()`, which sends `DELETE /project-{id}/api/v1/v2/ifc-objects/{id}?building={buildingId}`. The same request works from a widget and answers `{"data":null}`.

**Observed (2026-11-01):** right after the DELETE, the object is still served by `GET /v2/ifc-objects/{id}` and still found by search. Only its `Custom` group (Created/Updated At/By) is gone. `getObjectInfo` keeps returning the cached record until the page reloads. Treat deletion as eventually consistent, and don't rely on the object disappearing at once.

#### Create, then delete with the UI's request

```js
const projectId = await StreamBIM.API.getProjectId();
const buildingId = await StreamBIM.API.getBuildingId();
const { position } = await StreamBIM.API.getCameraState();
const id = await StreamBIM.API.createObject({ center: position, name: 'Docs example (deleted)' });
const url = '/project-' + projectId + '/api/v1/v2/ifc-objects/' + id + '?building=' + buildingId;
const groupsBefore = JSON.parse(await StreamBIM.API.makeApiRequest({ url })).data.attributes.groups.map((g) => g.label);
const deleted = await StreamBIM.API.makeApiRequest({ url, method: 'DELETE' });
let after;
try {
  after = JSON.parse(await StreamBIM.API.makeApiRequest({ url })).data.attributes.groups.map((g) => g.label);
} catch (err) {
  after = 'not found';
}
return { id, groupsBefore, deleteResponse: deleted.trim(), groupsAfterDelete: after };
```
